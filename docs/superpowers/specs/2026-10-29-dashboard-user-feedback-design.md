# Dashboard 使用者反饋改版設計

日期：2026-10-29　狀態：待使用者確認

## 背景與目的

dashboard 的使用者是圖書館端負責採購的人員，他們拿這張表**決定要買哪些書、買幾本**。
試用後給了五點反饋。這五點歸成三件事：

- **信不信得過每一筆建議**（第 3 點）。要能回頭看到一筆建議是怎麼來的。
  即使已有 match_auditor，NLA 回傳的記錄仍可能不是原書（全庫實測配錯率 31.2%、
  稽核對人工標註的抓到率 96.1%，仍有少數漏網），所以畫面要讓人自己判斷配對對不對。
- **數字準不準**（第 4 點）。同一本書被多門課用到時不該重複計算。
- **看得到自己要看的那一塊**（第 1、2 點）。第 5 點是等待時心裡有底。

## 範圍與順序

五件事相對獨立，**依下列順序各自規劃與實作**（第 3 點放最後，因為它要展示
「冊數怎麼算」，要等第 4 點改完算法才有定論）：

1. 第 5 點：處理進度 log
2. 第 2、1 點：類別篩選、學系篩選同步（都是篩選，一起做）
3. 第 4 點：同一本書跨課程去重與合計
4. 第 3 點：單筆追溯畫面

## 目標、非目標、反目標

**目標**：採購人員能在 dashboard 上依學系、優先級、類別切出自己要看的書；
每本書只出現一列、冊數是合計後的結果；能展開任一列看到完整決策過程。

**非目標**：
- 追溯畫面**只讀**，不在畫面上核准或退回；放行仍用現有命令列審核（`main review`）。
- 不改 match_auditor 的判斷邏輯。
- 不在這次決定合併後的冊數上限數字（見第 4 點）。
- 不做時間預估（使用者只要 log）。
- 不做視覺原型，使用者選擇用文字描述。

**反目標（技術上做完了也算失敗）**：
- 資料庫、CSV 匯出、dashboard 三邊的冊數或筆數不一致。
- 去重後看不出這本書被哪幾門課用到。
- 套了學系篩選後 KPI、圖表、明細表的筆數沒有跟著變。

## 各部分設計

### 第 5 點：處理進度 log

使用者決定（2026-10-29，兩次變更後的最終版）：**把終端機的文字輸出搬到網頁**，取代 mermaid 流程圖。
不分節點做進度條，只要像終端機那樣的逐行文字，例如 `[validator] OK [    1/65] 書名…`。

- **來源**：各節點本來就用 `print()` 印出 `[ 3/65]` 這類進度行，不另外建立進度資料結構。
- **節點名稱前綴**：每一行前面加 `[節點名稱] `，讓人看得出這行是哪個節點印的。
- **過濾**：只收 pipeline 自己 `print()` 出來的行；uvicorn 的 `INFO: ... GET /status` 存取日誌
  不經過 `print()`，天生不會進來（已實測：複製器記到 3 行 print、0 行存取日誌）。
- **錯誤**：traceback 走 stderr，也要一併收進來，否則看不到錯誤。
- **終端機照舊**：複製只是多存一份，終端機的輸出不變。
- 流程圖移除後，條件邊（重推迴路）與「match_auditor 送待審」的語意改以區塊下方一小段文字說明。

先前做過「每個節點一列、已處理 X / 共 Y 本、進度條」的版本，使用者看過後改要終端文字，
該版本（`progress.py`、節點的 `report()`、`pipeline_node_runs` 的四個進度欄位）已移除。

### 第 2 點：類別篩選

優先級按鈕列（全部 / HIGH / MEDIUM / LOW / SKIP / 待審核）維持原樣，旁邊加一組同樣樣式的
按鈕：**全部 / 指定 / 參考 / AI 推薦**。兩組可同時選，結果取交集。
類別的判定沿用現有 `_book_type_label`（AI 推薦 > 指定 > 參考）。

### 第 1 點：學系篩選同步

選了學系之後，KPI、圖表、明細表**都只顯示該學系資料庫裡所有已分析過的資料**
（不是只限這次按執行跑出來的那批）。學系按鈕與「按執行時分析哪些課」**共用同一個控制項**。

### 第 4 點：跨課程去重與合計（最終設計，2026-10-30 與使用者確認）

**一本書一筆建議**，冊數依「所有用到這本書的課」合計來算，現有館藏只扣一次。

**資料庫結構**（一支 Alembic migration，只加不改、可 downgrade）：
- `recommendations` 加 `book_key VARCHAR(500)`（唯一索引，允許 NULL）。一列的意義從「課程 × 書」變成「書」；
  `course_id`、`holding_id` 變成「代表課程 / 代表館藏」（該組館藏冊數最大者，同分取 id 最小）。
- 新表 `recommendation_courses(id, recommendation_id, course_id, citation_id, is_required, enrolled)`，
  `UNIQUE(recommendation_id, citation_id)`；`recommendation_id` 與 `citation_id` 的外鍵都是
  `ON DELETE CASCADE`——validator / librarian 會直接 `DELETE recommendations`，parser 會先刪舊 citations，
  沒有 cascade 這些節點會被外鍵擋住而崩潰。其他表不動。

**同一本書的認定 `book_key`**：
- 有效 ISBN（過檢查碼；ISBN-10 轉成 13 碼）→ `isbn:<13 碼>`。無效值（例如 Alma 記錄編號、格式錯誤的值）
  一律當成「沒有 ISBN」。不同的有效 ISBN 不合併（不同版次分開）。
- 沒有有效 ISBN → 依正規化書名分桶，桶內記錄完全相同者直接同組，其餘用 match_auditor 的判斷
  （規則＋LLM）決定是否同一本；**判斷失敗時不合併**（與 match_auditor 稽核時的預設相反）。
  有有效 ISBN 的書與沒有 ISBN 的同名書不合併。
- 判斷結果不存檔，每次重算（需要 LLM 的只有「沒有有效 ISBN、書名相同、記錄不完全相同」的少數組）。

**計算**（`_decide` 完全不改）：人數 = 各「不同課程」人數加總（同課重複只算一次）；
任一課指定 → 按指定算；館藏取冊數最大的一筆、任一筆是電子書就 SKIP；套 `max_purchase_copies`（維持可調，
具體數字等跑完分析再決定）。

**recommender**：永遠以全校資料計算（不再依 `course_ids` 限縮，否則合計只含選中的課而失真）；
冪等簽章 = (優先級, 冊數, 引用的書目集合)，簽章沒變就不重打 LLM、只刷新關聯表；
清掉不再存在的 `book_key` 以及舊格式（`book_key` 為 NULL）的列。理由的 prompt 要帶入「每門課各自的人數與
指定/參考」，否則 LLM 會把「一門指定、一門參考」寫成「兩門指定」（實測發生過）。

**畫面與讀取端**：一本書一列、一個建議冊數；「課程」欄列出所有用到的課並標明各自類別，`data-btypes`
放多個 token。優先級圖、館藏狀態圖、明細都數「書」，底一致。學系篩選：書只要有任一門課屬於所選學系就顯示，
冊數顯示全校合計，「課程」欄標出屬於所選學系的課。讀取端三處：dashboard `_load_data`、`main.py` 報表、
`/export/recommendations`。

**篩選語意**：一本書可能同時被某課指定、被另一課列為參考，只要有任何一門課符合，該類別的篩選就會顯示這本書。

### 第 3 點：單筆追溯畫面（最終設計，2026-10-30，依去重後的資料結構重新對齊）

點一本書那一列的展開鈕，在下方展開這本書的決策過程；**只讀**，不在畫面上核准或退回。五段：

1. **課綱原文**：用到這本書的每一門課各一份——書目被提到的那一段（`raw_mention`，通常很短）放在前面，
   完整課綱收在可展開區塊（中位數 207 字，但最長 32454 字，所以截斷並標明原長度）。
2. **解析結果**：每個書目一列——書名、作者、版次、ISBN、出版社、年份、類別（指定／參考／AI 推薦）、
   解析信心度、計算當時該課的人數。
3. **驗證配對**（重點）：「原書」與「配到的書」並排，加上 match_auditor 的判定（同一本／配錯）、
   用規則或 LLM、理由，以及人工審核狀態。**每個書目各自配對**，所以相同的配對結果合併成一項並標明涵蓋幾個書目，
   不同的才分開列（實測：231 本跨書目的書裡只有 15 本的配對結果不完全相同）。
4. **Alma 館藏**：代表館藏的狀態、現有冊數、Alma 記錄編號、比對到的版次；若各書目的館藏不一致要註明。
5. **冊數怎麼算**：各課人數 → 合計 → ÷ 每本服務人數（進位）→ 扣現有館藏（只扣一次）→ 套上限 → 優先級。
   資料庫只存結果不存算式，所以**用同一套 `merge_group` 重算**；重算結果與資料庫存的建議不同時
   （上限、館藏或資料在建議產生後改過），要明確標出差異，而不是默默顯示不同的數字。

**範圍**：只有採購建議列（一本書一筆）有展開鈕；「待審核」列是書目層級、沒有採購建議，不做追溯。
**資料來源**：新端點 `GET /trace/{id}` 回傳已逸出的 HTML 片段（課綱與書名都是第三方文字，一律 `html.escape`），
前端第一次展開時才取、取過不再取。

## 限制

- dashboard 是單檔 FastAPI + f-string 產生的 HTML，CSS/JS 的大括號要寫成雙括號。
- 沿用 `db/filters.py` 的 `purchasable()`，配錯且未經人工放行的書不得進採購建議。
- 現有 97 個測試必須維持通過。
- 現有 recommendations 資料要有遷移或重算的路徑（粒度從「課程×書」變成「書」）。

## 留給實作者決定

- 各節點進度的分母怎麼取、log 訊息存哪裡。
- 展開畫面的資料用一支 API 還是多支。

## 設計者自行決定的部分（請使用者過目）

- 學系按鈕與執行共用同一個控制項。
- 合併改在 recommender，不只在畫面上合併（資料庫、CSV、dashboard 三邊一致）。
- 版次不合併：不同的有效 ISBN 一律分開，寧可多買一套，不要把不同的書當成同一本。
- recommender 不再依 `course_ids` 限縮，永遠算全校。
- 課程欄每門課旁標類別。
- 第 5 段冊數展開時重算而非另存。
- 時間預估不納入。
- 移除流程圖時，一併刪掉不再使用的 `static/mermaid.min.js`（約 3.2 MB）與 dashboard 的
  `/static` 掛載（該目錄只剩這一個檔案，檔案刪掉後目錄不存在，掛載會讓 import 失敗）。
- log 存在記憶體，只保留最近 2000 行，每次按執行時清空，伺服器重啟就沒了；
  重新整理頁面時要能拿回目前這次執行已有的行。
- 若同一本書的幾筆 citation 中有的被擋（配錯或被退回），只排除被擋的那幾筆，
  其餘照常合計；全被擋則整本不顯示。
