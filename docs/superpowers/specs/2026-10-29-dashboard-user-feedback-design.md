# Dashboard 使用者反饋改版設計

日期：2026-10-29　狀態：待使用者確認

## 背景與目的

dashboard 的使用者是圖書館端負責採購的人員，他們拿這張表**決定要買哪些書、買幾本**。
試用後給了五點反饋。這五點歸成三件事：

- **信不信得過每一筆建議**（第 3 點）。要能回頭看到一筆建議是怎麼來的。
  即使已有 match_auditor，NLA 回傳的記錄仍可能不是原書（全庫實測配錯率 31.2%、
  稽核對人工標註的抓到率 96.1%，仍有少數漏網），所以畫面要讓人自己判斷配對對不對。
- **數字準不準**（第 4 點）。同一本書被多門課用到時不該重複計算。
- **看得到自己要看的那一塊**（第 1、2 點）。第 5 點是等待時心裡有底。

## 範圍與順序

五件事相對獨立，**依下列順序各自規劃與實作**（第 3 點放最後，因為它要展示
「冊數怎麼算」，要等第 4 點改完算法才有定論）：

1. 第 5 點：處理進度 log
2. 第 2、1 點：類別篩選、學系篩選同步（都是篩選，一起做）
3. 第 4 點：同一本書跨課程去重與合計
4. 第 3 點：單筆追溯畫面

## 目標、非目標、反目標

**目標**：採購人員能在 dashboard 上依學系、優先級、類別切出自己要看的書；
每本書只出現一列、冊數是合計後的結果；能展開任一列看到完整決策過程。

**非目標**：
- 追溯畫面**只讀**，不在畫面上核准或退回；放行仍用現有命令列審核（`main review`）。
- 不改 match_auditor 的判斷邏輯。
- 不在這次決定合併後的冊數上限數字（見第 4 點）。
- 不做時間預估（使用者只要 log）。
- 不做視覺原型，使用者選擇用文字描述。

**反目標（技術上做完了也算失敗）**：
- 資料庫、CSV 匯出、dashboard 三邊的冊數或筆數不一致。
- 去重後看不出這本書被哪幾門課用到。
- 套了學系篩選後 KPI、圖表、明細表的筆數沒有跟著變。

## 各部分設計

### 第 5 點：處理進度 log

使用者決定：**log 取代 mermaid 流程圖**（2026-10-29 變更）。「Pipeline 進度」區塊改成依節點順序
列出每個節點一行：狀態（未開始 / 執行中 / 完成 / 錯誤，沿用現有狀態色）、
「已處理 X / 共 Y 本」、最新一行處理訊息。沒有迴圈的節點（crawler、human_review）只顯示狀態。
目前 `/status` 只回各表的現有筆數，**沒有分母**，實作時要先定義各節點「共 Y」從哪來
（例如 validator 的待驗證 citation 數、match_auditor 的待稽核數）。
流程圖移除後，條件邊（重推迴路）與「match_auditor 送待審」的語意改以區塊下方一小段文字說明。

### 第 2 點：類別篩選

優先級按鈕列（全部 / HIGH / MEDIUM / LOW / SKIP / 待審核）維持原樣，旁邊加一組同樣樣式的
按鈕：**全部 / 指定 / 參考 / AI 推薦**。兩組可同時選，結果取交集。
類別的判定沿用現有 `_book_type_label`（AI 推薦 > 指定 > 參考）。

### 第 1 點：學系篩選同步

選了學系之後，KPI、圖表、明細表**都只顯示該學系資料庫裡所有已分析過的資料**
（不是只限這次按執行跑出來的那批）。學系按鈕與「按執行時分析哪些課」**共用同一個控制項**。

### 第 4 點：跨課程去重與合計

- **同一本書**：ISBN 相同；沒有 ISBN 就比書名。
- **冊數**：需求 = ceil(所有用到這本書的課的選課人數合計 ÷ 每本服務人數)，
  現有實體館藏**只扣一次**，再套單本上限。
- **優先級**：只要有一門課指定，整本書按指定算（取最嚴格的）。
- **上限**：沿用 config 的 `max_purchase_copies`（現為 5），維持可調；
  **具體數字等做出來、跑完分析再決定**，使用者已確認原本的 5 不適用於合計後的數字。
- **畫面**：一本書一列、一個建議冊數。「課程」欄列出所有用到的課，每門課旁標明它自己的類別。
- **篩選語意**：一本書可能同時被某課指定、被另一課列為參考。只要有任何一門課符合，
  該類別的篩選就會顯示這本書，所以同一本書可同時出現在「指定」和「參考」兩個篩選結果。
- **實作位置**：改在 recommender，讓資料庫、CSV、dashboard 三邊一致，
  而不是只在畫面上合併。

### 第 3 點：單筆追溯畫面

點一列會在下方展開，依序顯示五段：

1. **課綱原文**：這本書在課綱裡被提到的那段；完整課綱收在可展開區塊。
2. **解析結果**：書名、作者、版次、ISBN、信心度、指定或參考。
3. **驗證配對**（重點）：原書與配到的書**左右並排**，並顯示 match_auditor 的判定
   （同一本或配錯）與理由。
4. **Alma 館藏**：館藏狀態、現有冊數。
5. **冊數怎麼算**：各課人數、合計、除以每本服務人數、扣現有館藏、套上限、優先級。

一本書有多門課時，第 1、2 段每門課各一份，第 3 到 5 段只有一份。
資料庫只存結果、不存算式，所以第 5 段在展開時**用同一套 `_decide` 算法重算**。
副作用：若之後改了上限，展開畫面顯示的是新設定，可能與當時跑出的數字不同；
實作者應讓這個差異可被察覺，而不是默默顯示不同數字。

## 限制

- dashboard 是單檔 FastAPI + f-string 產生的 HTML，CSS/JS 的大括號要寫成雙括號。
- 進度區的節點順序必須與 `graph.NODE_NAMES` 一致（`/status` 依此順序回傳）。
- 沿用 `db/filters.py` 的 `purchasable()`，配錯且未經人工放行的書不得進採購建議。
- 現有 97 個測試必須維持通過。
- 現有 recommendations 資料要有遷移或重算的路徑（粒度從「課程×書」變成「書」）。

## 留給實作者決定

- 合併後的 recommendation 資料表結構（目前以 `course_id` 與 `holding_id` 為鍵）。
- 各節點進度的分母怎麼取、log 訊息存哪裡。
- 展開畫面的資料用一支 API 還是多支。

## 設計者自行決定的部分（請使用者過目）

- 學系按鈕與執行共用同一個控制項。
- 合併改在 recommender，不只在畫面上合併。
- 課程欄每門課旁標類別。
- 第 5 段冊數展開時重算而非另存。
- 時間預估不納入。
- 移除流程圖時，一併刪掉不再使用的 `static/mermaid.min.js`（約 3.2 MB）與 dashboard 的
  `/static` 掛載（該目錄只剩這一個檔案，檔案刪掉後目錄不存在，掛載會讓 import 失敗）。
- 「最新一行處理訊息」只保留每個節點最後一行，不存歷史 log。
- 若同一本書的幾筆 citation 中有的被擋（配錯或被退回），只排除被擋的那幾筆，
  其餘照常合計；全被擋則整本不顯示。
