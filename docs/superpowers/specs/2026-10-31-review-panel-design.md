# 人工審核區塊設計

日期：2026-10-31　狀態：待使用者確認

## 背景與目的

資料庫裡 1280 本書被標成 `pending`（待人工審核），**核准與退回都是 0 筆，從來沒有人處理過**。
審核只有命令列 `main review`：逐筆、互動式、依課名排序，沒有搜尋、批次或分類。儀表板能看到這些列、
能展開看原因（追溯畫面），但不能處理。

1280 筆的組成與「不處理」的後果截然不同（2026-10-31 實測）：

| 原因 | 筆數 | 現在在採購清單嗎 | 不處理的風險 |
|---|---|---|---|
| 配對被稽核判為配錯 | 746（規則 261、LLM 485） | **不在**（被 `purchasable()` 擋下） | 課程真正要用的書沒被建議採購 |
| 驗證階段查無此書 | 532（其中 19 筆信心也偏低） | **仍在**：426 本建議、992 冊、262 本是最高優先級 | 買了查不到的東西；館藏是用原書名直接查的，不可靠 |
| 判同一本但仍待審 | 2 | 1 筆在 | — |

同一本書常被多門課重複列出：746 筆配錯只有 537 組不同的（原書、配到的書），532 筆查無此書只有 426 個不同書名，
**實際要做的決定約 963 個**。

目標使用者是圖書館採購人員，不熟悉本系統的內部機制。

## 範圍與順序

分三步，**本文件的設計細節只涵蓋第一步**；第二、三步的決定已與使用者確認，記在最後兩節，各自開工前再確認一次。

1. **第一步（唯讀）**：儀表板新增獨立的「人工審核」區塊，把待審的書分類、合併成「一組一本書」、排出處理順序、
   可展開看證據；採購表標出「未驗證」的建議。**不改任何資料。**
2. **第二步（採購冊數由使用者決定）**：採購表每本書多一欄可填的「決定冊數」，系統建議只是參考。
   只在讀取時疊一層人的決定，不動 librarian、recommender，風險較小，所以排在審核按鈕之前。
3. **第三步（審核動作）**：在審核區塊上加處理按鈕、資料庫欄位、「套用審核結果」。會改採購結果；使用者已決定先做這一步（排在第二步之前）。

## 目標、非目標、反目標

**目標**：採購人員打開儀表板就能看懂「有哪些書卡住、為什麼、各有多重要」，並依影響大小逐組檢視。
讓人一眼看出採購清單裡哪些建議是**未驗證**的。

**非目標（第一步）**：
- 不提供核准／退回／輸入書名等任何會寫資料庫的動作。
- 不改 match_auditor、validator 的判斷，不改 `purchasable()` 的篩選規則。
- 不替「查無此書」擋下採購（使用者決定：維持現狀，只加標記，避免書悄悄消失）。
- 不記錄審核者（使用者決定：先不做）。
- 不處理 `nla.py` 的匹配修正（另案）。

**反目標（做完了也算失敗）**：
- 審核區塊與採購表、KPI 的筆數對不起來，使用者分不清「筆」與「組」。
- 把「書名相同但作者不同」的不同書合併成一組（這正是配錯的成因）。
- 區塊讓採購表的 CSV 匯出多出文字（匯出讀每格 `textContent`）。

## 第一步設計

### 分組

- 分三類（`kind`）：`mismatch`（稽核判配錯）、`notfound`（`verified=False`）、`other`（其餘待審）。
  一筆同時符合時，配錯優先於查無此書。
- 分組鍵（書名一律用 match_auditor 的 `_norm` 正規化）：
  - 配錯：（原書名、配到的書名）。**配到的書名必須在鍵裡**：同名不同作者的書配到不同本，必須分開。
  - 查無此書：原書名。
  - 其他：每筆書目自成一組。
- 每組帶：原書名／作者、配到的書名／作者（查無此書沒有）、來源、判定者（規則／LLM）、理由、是否信心偏低、
  用到的課（名稱與各自人數，**同一門課只算一次**）、書目數、人數合計、涵蓋的書目 id 清單。
- 查無此書的組另帶「所在採購建議的優先級與冊數」（該書目若在某筆採購建議的關聯表裡）；配錯的組標示「已擋下」。

### 排序（讓人先處理影響大的）

- 查無此書：優先級（HIGH → MEDIUM → LOW → SKIP → 不在清單）、再依人數合計由大到小。
- 配錯與其他：人數合計由大到小、再依書名。

### 畫面

- 新增獨立卡片「人工審核」（`id="review"`），放在採購明細之後；KPI 的「待人工審核」卡片可跳到它。
- 卡片頂端三個分頁：**配錯 / 查無此書 / 其他**，每個標示「N 組（M 筆書目）」，避免與 KPI 的筆數混淆。
- 每組一列：原書（書名、作者）｜配到的書（或「查無記錄（來源）」）｜原因｜用到的課（含各課人數）｜人數合計｜
  採購清單狀況｜▸ 展開。
- ▸ 展開沿用追溯畫面：課綱、解析、配對、館藏；一組內的所有書目一次顯示，相同的配對自動合併。
- 學系篩選照常套用：組內只計所選學系的書目；某分頁沒有組時顯示一句說明，不報錯。
- 沒有任何待審時，整張卡片顯示「目前沒有待審書目」。
- 卡片標頭有「匯出待審清單」連結（指向現有的 `/export/pending`）。

### 採購明細表的調整

- **待審核的列從採購表移除**（它們有自己的區塊了）；優先級篩選的「待審核」按鈕改成跳到審核區塊的連結；
  匯出面板的「待審核」勾選項移除（待審清單改由審核卡片匯出）。優先級圖與 KPI 的「待審核」長條／卡片不動。
- **「未驗證」標記**：建議的任一書目驗證時查無此書，書名格後加一個小標記，滑鼠停留說明
  「驗證階段查無此書，館藏是用書名直接查詢的結果」。標記用 CSS 畫（不含文字節點），
  列上加 `data-unverified="1"`。

### 追溯端點

- `GET /trace/pending?ids=1&ids=2…` 取代 `GET /trace/pending/{vb_id}`：一組可含多個書目。
  至多 50 個 id；沒有 id 或格式錯誤回 400；全部都已不在待審狀態回 404；部分已處理只顯示仍待審的。

## 設計者自行決定的部分（請使用者過目）

- 審核區塊放在採購明細**之後**（採購表仍是主要內容）。
- 待審列從採購表移除，而不是兩邊都放（避免重複與計數混亂）。
- 分組鍵包含配到的書名；查無此書只看原書名。
- 排序依「對採購的影響」而不是課名。
- 「未驗證」用 CSS 標記，不放文字。
- 單筆端點 `/trace/pending/{vb_id}` 改成多 id 的查詢式端點。

## 第二步：採購冊數由使用者決定（2026-10-31 與使用者確認）

動機：被上限截斷的書（85 本，例如需求 26 本）要買幾本，是採購人員依預算與經驗判斷的事，不該由一個全域數字決定；
系統建議留作參考，最後由人填。

- **獨立一張小表**，以 `book_key`（同一本書的識別）為鍵，存「決定冊數」、決定當時的系統建議、決定時間。
  **不能存在 `recommendations` 上**：該表是衍生資料，librarian 更新館藏、recommender 重算時會被刪掉重建，人的決定會跟著消失。
- 採購表冊數旁多一欄「決定冊數」輸入框；**留空＝採用系統建議**；填 0＝這次不買（書仍留在清單，與審核的「退回」不同）。
- 每列顯示「需求 N → 建議 M」，被上限截斷時一眼看得出；不再悄悄截斷。全域上限仍是 5，作為系統建議的預設，不另做調整介面。
- 決定過期：存下決定當時的系統建議，之後系統建議變了就標示「建議已從 A 變成 B」，不悄悄沿用。
- KPI 分「系統建議」與「採用數」；匯出 CSV 多「決定冊數」「最終採購數」兩欄。
- 技術限制：匯出讀每格 `textContent`，輸入框的值不在其中，匯出程式要明確讀輸入框。
- 只記時間，不記是誰（使用者決定先不做審核者）。

## 第三步：審核動作（2026-10-31，使用者決定做；設計細節）

### 動作與語意

按鈕依類別不同（使用者提出）。「買原書」與「輸入書名加入」是同一件事：**以這個書名採購**。

| 類別 | 動作 | `review_status` | `review_choice` | 採購書名 |
|---|---|---|---|---|
| 配錯 | 買配對到的書 | approved | matched | 無（沿用驗證器配到的） |
| 配錯 | 買原書 | approved | original | 原書名、原作者；ISBN 取原書 ISBN（過檢查碼才算，否則空） |
| 配錯／查無此書／其他 | 都不買／捨棄 | rejected | none | 無 |
| 查無此書 | 輸入書名加入採購清單 | approved | custom | 使用者輸入的書名（預填原書名）；ISBN 選填，過檢查碼才收，作者留空 |
| 其他 | 買這本書 | approved | matched | 無 |

- 動作套用到**一組的所有書目**（一本書被多門課列出，按一次全部生效）。
- 只處理仍是 `pending` 的書目；已被別人處理的不覆蓋，回報跳過了幾筆。
- **不重新驗證**（使用者決定）：輸入的書名／ISBN 直接信任。**不記審核者**（使用者決定先不做），只記時間。
- 查無此書在審核前不擋採購（使用者決定）；放行或輸入後，「未驗證」標記消失（人已確認）。

### 資料庫（一支 migration，只加欄位、可 downgrade）

`verified_books` 新增：`purchase_title`、`purchase_authors`（JSON 文字）、`purchase_isbn`、`review_choice`、
`reviewed_at`、`review_applied_at`。

- **採購書名不覆蓋 `canonical_*`**：那是驗證器配到的證據，審核要留著。下游一律讀 model 的 `buy_title / buy_authors / buy_isbn`
  （hybrid 屬性）：`purchase_title` 有值就用採購欄位，否則用 `canonical_*`。**ISBN 不能用 coalesce**：「買原書」沒有 ISBN 時，
  不能沿用配到那一本的 ISBN（那正是配錯的來源）。
- 決定會留住：validator 本來就不重驗 approved／rejected 的書；match_auditor 只處理 `pairing_verdict` 為空的列。
  （仍加一個測試把這個行為釘住。）

### 套用審核結果

決定當下只寫資料庫；退回在讀取端立刻生效（`purchasable()` 已排除）。**放行的書要等「套用」後才會出現在採購清單**，
因為採購建議是 recommender 算出的衍生資料。

「套用」是背景工作（`POST /review/apply`），對 `review_status='approved'` 且 `review_applied_at` 為空的書：
1. 有採購書名、或還沒有館藏列者，用採購書名／ISBN 重查 Alma（librarian 新增 `recheck_holdings(vb_ids)`，沿用
   `_check_one` 與 `_stage_save`；館藏有變就連帶刪掉指向它的舊建議）。
2. `recommender_node` 重算全校（簽章沒變不打 LLM；只有新增或數字變了的書才寫新理由）。
3. 成功才標 `review_applied_at`；任何一步失敗就不標，下次可重試，不留半套。

與 `/run` 共用鎖、狀態與執行紀錄（同時只能有一個）；結束後頁面自動重整（既有機制）。
不在「決定當下」就重查館藏：批次決定上百筆會卡住請求，而且重查會連帶刪掉指向舊館藏的建議，書在套用完成前就從清單消失。

### 撤銷

`POST /review/undo`：把有 `review_choice` 的書改回 `pending`，清掉選擇與採購欄位。若原本是 `original`／`custom`，
**一併刪除那本的館藏列（含指向它的建議）**：它是用採購書名查的，留著會讓之後改選「買配對到的書」時用到錯的館藏。

### 畫面

- 審核卡片的每組：配錯三顆按鈕（買原書／買配對到的書／都不買）；查無此書一個書名輸入框（預填原書名）、ISBN 輸入框（選填）、
  「加入採購清單」與「捨棄」；其他兩顆（買這本書／都不買）。成功後該組從待審分頁移走，錯誤顯示在該列。
- 多選批次：只提供「買配對到的書」與「都不買」，並跳出確認視窗寫明組數與書目數。
- 新增第四個分頁「已決定」：每組顯示決定、採購書名、狀態（待套用／已套用）與「撤銷」。
- 卡片頂端顯示「N 筆決定待套用 ［套用並重算採購建議］」，有工作在跑時按鈕停用。

### 端點（都是 JSON 的 POST，不用 GET 改資料）

- `POST /review/decide`：`{ids, action, title?, isbn?}`；`action ∈ matched/original/custom/none`；
  書名空白或超過 500 字、ISBN 格式錯誤、id 超過 200 個、未知的 action 回 400，且不寫入任何東西。
- `POST /review/undo`：`{ids}`。
- `POST /review/apply`：沒有待套用的書、或已有工作在跑，回 `{ok: false, message}`。

### 限制與取捨

- 儀表板仍沒有登入機制、預設只綁 `127.0.0.1`；這是第一個會改採購結果的畫面，開放區網前要另外做登入。
- 「買原書」沒有 ISBN 時只能用書名查館藏，Alma 查詢不看作者，可能混到同名他書；畫面標示
  「以書名查詢，可能含同名他書」，不假裝準確。
- 命令列 `main review` 的核准／退回改走同一份邏輯（記錄選擇與時間，也會出現在「已決定」）；「修正書名」維持原行為。

## 限制

- dashboard 是單檔 FastAPI + f-string 產生的 HTML，CSS/JS 的大括號要寫成雙括號。
- 匯出 CSV 讀每格 `textContent`：任何標記、按鈕都不能放文字。
- 現有 222 個測試必須維持通過（會因移除待審列而改的測試，要明確改並說明）。

## 留給實作者決定

- 分頁、卡片的視覺細節與配色（沿用現有的 `.tag`、`.pill`、`--border` 等變數）。
- 組內書目很多時的展開樣式（沿用追溯畫面的 `<details>`）。
